## システム概要

### 目的
商品・サービスの広告コピー（Excel）を一括チェックし、NG/注意表現を自動検出するシステム

### 処理フロー
```
Excel アップロード (S3)
    ↓
EventBridge 自動検知
    ↓
Step Functions 起動
    ↓
① Splitter: Excel → 行データ配列
    ↓
② Processor: 各行を並列処理（最大500並列）
    ↓
③ Combiner: 結果統合 → Excel出力
    ↓
結果 Excel (S3)
```

### 処理規模
- **想定行数**: 100〜10,000行/ファイル
- **並列度**: 最大500並列
- **チェック項目**: 8項目/行
- **参照キーワード**: 227種類

## 技術選定

### 1. **Step Functions vs EC2/ECS**

| 項目 | Step Functions (採用) | EC2/ECS |
|------|----------------------|---------|
| **スケーラビリティ** | ✅ 自動スケール、最大500並列 | △ 手動スケーリング設定必要 |
| **運用負荷** | ✅ サーバーレス、保守不要 | ✗ サーバー管理、パッチ適用 |
| **コスト** | ✅ 使用量課金、アイドル時ゼロ | △ 常時稼働コスト |
| **可視性** | ✅ 実行状況が可視化 | △ 独自実装必要 |
| **リトライ/エラー処理** | ✅ 宣言的に定義可能 | △ コード実装必要 |
| **開発速度** | ✅ 高速 (JSON定義) | △ 低速 (インフラ構築) |

**結論**: サーバーレス、自動スケーリング、運用負荷の低さから **Step Functions を採用**

---

### 2. **Lambda vs Fargate**

| 項目 | Lambda (採用) | Fargate |
|------|--------------|---------|
| **起動時間** | ✅ ミリ秒 (コールドスタート除く) | △ 秒単位 |
| **コスト** | ✅ 100ms単位課金 | △ 秒単位課金、最低1vCPU必要 |
| **スケーリング** | ✅ 自動、即座 | △ やや遅い |
| **実行時間制限** | △ 最大15分 | ✅ 制限なし |
| **メモリ** | △ 最大10GB | ✅ 最大120GB |

**結論**: 
- **Splitter/Combiner**: 15分以内で完了 → Lambda
- **Processor**: 1行あたり数秒〜数十秒 → Lambda で十分

---

### 3. **Map State vs SQS + Lambda**

| 項目 | Map State (採用) | SQS + Lambda |
|------|-----------------|--------------|
| **実装複雑度** | ✅ シンプル (JSON定義) | △ SQS管理、デッドレターキュー設定 |
| **可視性** | ✅ Step Functions コンソールで確認 | △ CloudWatch/SQS コンソール |
| **並列度制御** | ✅ MaxConcurrency で簡単設定 | △ Lambda 予約済み同時実行数 |
| **エラーハンドリング** | ✅ Retry/Catch 設定 | △ DLQ + カスタムコード |
| **コスト** | △ State遷移課金 | ✅ SQSは安価 |

**結論**: 実装のシンプルさ、可視性の高さから **Map State を採用**

---

### 4. **S3 vs DynamoDB (結果保存)**

| 項目 | S3 (採用) | DynamoDB |
|------|----------|----------|
| **コスト** | ✅ 安価 ($0.023/GB) | △ 高価 (読み書き課金) |
| **容量制限** | ✅ 無制限 | △ 400KB/項目 |
| **クエリ** | △ 不要 (Combinerが順次読み込み) | ✅ 高速クエリ可能 |
| **データ永続性** | ✅ 高い (11 9s) | ✅ 高い |

**結論**: 
- 各行の結果は小さいJSON (数KB〜数十KB)
- クエリ不要 (execution_id で一括取得)
- → **S3 を採用** (コスト優位)

---

### 5. **EventBridge vs S3 Event Notification**

| 項目 | EventBridge (採用) | S3 Event Notification |
|------|--------------------|----------------------|
| **イベントフィルタ** | ✅ 複雑な条件設定可能 | △ 限定的 |
| **ターゲット** | ✅ 複数ターゲット可能 | △ Lambda/SNS/SQS のみ |
| **拡張性** | ✅ 他AWSサービス連携容易 | △ 限定的 |
| **設定** | ✅ 一元管理 | △ バケット設定に依存 |

**結論**: 将来的な拡張性、柔軟性から **EventBridge を採用**

---

### 6. **Stub Mode vs Production Mode**

| モード | 用途 | LLM API | VPC | 環境 |
|--------|------|---------|-----|------|
| **Stub** | 動作検証、負荷テスト | モック応答 | 不要 | Sandbox |
| **Production** | 本番運用 | 実際の LiteLLM API | 必要 | Dev/Prod |

**段階的移行**:
1. ✅ **Phase 1** (現在): Stub モード + Sandbox環境
   - インフラ構成検証
   - Step Functions 動作確認
   - EventBridge 自動トリガー検証

2. ⏭️ **Phase 2**: Production モード + Dev環境
   - VPC 設定
   - LiteLLM API 接続テスト
   - 実際のチェック結果検証

3. ⏭️ **Phase 3**: Production環境デプロイ
   - 本番運用開始

## コスト試算

### 前提条件
- **月間処理ファイル数**: 100ファイル
- **平均行数**: 1,000行/ファイル
- **合計処理行数**: 100,000行/月

### AWS料金 (東京リージョン)

#### **1. Step Functions**
- **State 遷移数**:
  - 1ファイルあたり: 1 (SplitExcel) + 1,000 (ProcessRows) + 1 (CombineResults) = 1,002 遷移
  - 月間: 1,002 × 100 = 100,200 遷移
  - **無料枠**: 4,000 遷移/月
  - **課金対象**: 96,200 遷移
- **料金**: $0.025 / 1,000遷移 = **$2.41/月**

#### **2. Lambda**

**Splitter**:
- **実行回数**: 100回/月
- **実行時間**: 平均 30秒/回
- **メモリ**: 2048 MB
- **GB-秒**: (2048/1024) × 30 × 100 = 6,000 GB-秒
- **料金**: $0.0000166667/GB-秒 × 6,000 = **$0.10/月**

**Processor**:
- **実行回数**: 100,000回/月
- **実行時間**: 平均 5秒/回 (stub: 1秒、本番: 10秒想定)
- **メモリ**: 1024 MB
- **GB-秒**: (1024/1024) × 5 × 100,000 = 500,000 GB-秒
- **無料枠**: 400,000 GB-秒/月
- **課金対象**: 100,000 GB-秒
- **料金**: $0.0000166667/GB-秒 × 100,000 = **$1.67/月**

**Combiner**:
- **実行回数**: 100回/月
- **実行時間**: 平均 60秒/回
- **メモリ**: 2048 MB
- **GB-秒**: (2048/1024) × 60 × 100 = 12,000 GB-秒
- **料金**: $0.0000166667/GB-秒 × 12,000 = **$0.20/月**

**Lambda 合計**: **$1.97/月**

#### **3. S3**
- **ストレージ**: 10 GB (input + output + results)
- **料金**: $0.025/GB × 10 = **$0.25/月**
- **PUT リクエスト**: 100,100回 (input: 100 + results: 100,000)
- **料金**: $0.0047 / 1,000 × 100.1 = **$0.47/月**
- **GET リクエスト**: 100,100回
- **料金**: $0.00037 / 1,000 × 100.1 = **$0.04/月**

**S3 合計**: **$0.76/月**

#### **4. EventBridge**
- **カスタムイベント**: 100イベント/月
- **無料枠**: 該当 (数百万イベントまで無料)
- **料金**: **$0/月**

#### **5. CloudWatch Logs**
- **ログ取り込み**: 5 GB/月
- **料金**: $0.76/GB × 5 = **$3.80/月**
- **ストレージ**: 5 GB/月
- **料金**: $0.033/GB × 5 = **$0.17/月**

**CloudWatch 合計**: **$3.97/月**

### **月間合計コスト**: 約 **$9.11/月** (約 ¥1,400/月)

### **年間コスト**: 約 **$109/年** (約 ¥16,800/年)

### コスト最適化の検討

#### **Stub モード vs Production モード**
- **Stub**: Processor 1秒/回 → $1.67/月
- **Production**: Processor 10秒/回 → $16.67/月
- **差額**: 約 $15/月

#### **大規模処理時 (10,000行/ファイル)**
- **Step Functions**: $24.05/月 (約10倍)
- **Lambda**: $19.70/月 (約10倍)
- **月間合計**: 約 **$50/月** (約 ¥7,700/月)

#### **コスト削減案**
1. **Lambda メモリ最適化**: 使用率が低い場合、メモリを削減
2. **CloudWatch Logs 保持期間**: デフォルト無期限 → 30日に設定
3. **S3 ライフサイクル**: results/ を1日後削除、output/ を90日後削除
4. **予約済み同時実行数**: 本当に500必要か検証 (現在は最大並列度)

### 技術的課題と対応

#### **課題1: LLM API レート制限**
- **対策**: Processor でリトライ設定、指数バックオフ実装

#### **課題2: 大量行数 (10,000行以上)**
- **対策**: 
  - Splitter でファイル分割 (5,000行ずつ)
  - または Step Functions の Distributed Map 検討

#### **課題3: VPC 配置による Lambda コールドスタート遅延**
- **対策**:
  - Provisioned Concurrency (オプション)
  - Lambda WarmerによるWarm-up (オプション)

#### **課題4: Excel マクロ (.xlsm) 対応**
- **現状**: openpyxl で `keep_vba=True`, `data_only=True` で対応済み
- **課題**: マクロ実行は不可
- **対策**: 必要に応じて openpyxl のバージョンアップ
